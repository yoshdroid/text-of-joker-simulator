# Architecture

## 推奨構成

- `main` プロセスがゲーム状態の唯一の正本を持つ
- `player` プロセスは状態を受け取り、行動候補を返す
- 通信は `stdin/stdout` の `JSON Lines` を基本にする
- 標準エラー出力はデバッグ専用に分離する

## ディレクトリ方針

- `src/tojs/`: 実装本体
- `tests/`: 先に書くテスト
- `configs/`: レギュレーション
- `docs/`: 設計メモ

## 能力 JSON の扱い

カードプールに入っている `abilities` は、当面は次の 2 段階で扱うのが安全です。

1. まずは JSON を壊さず構造として保持する
2. 実装可能なものから `event -> condition -> effect` の内部 DSL へ段階変換する

最初から自然文を完全解釈しようとすると不確実性が高いため、カードプール JSON はソースデータとして保持し、必要に応じて手で正規化する方針が現実的です。

## セキュリティ方針

### 第一案: Docker Desktop

- `--network none`
- 読み取り専用ルートファイルシステム
- CPU / memory / process 数を制限
- 競技用 AI の入出力専用ディレクトリだけをマウント
- タイムアウト超過時はメインプロセス側で強制終了

### Windows 代替案

Docker 以外では、次の組み合わせが候補です。

- Windows Job Object で CPU 時間・メモリ・子プロセス数を制限
- 低権限ユーザーでプレイヤーを起動
- 一時ディレクトリを分離
- タイムアウト監視

完全な隔離強度は Docker の方が高いため、他者作成プレイヤーを実行する前提なら Docker を第一候補にするのが無難です。

## ゲームエンジン実装順

1. レギュレーション / デッキ検証
2. ラウンド進行の骨格
3. ドロー、CP、召喚、アタックなどの基本アクション
4. 自動発火トリガーと任意使用インターセプト
5. カード別能力解決

## 確定した基本仕様

- 1 回のアタック宣言に対して、相手が選べるブロッカーは 1 体だけ
- BP ダメージはターン中継続し、ターン終了時に最大値へ回復する
- プレイヤープログラムの言語は `stdio` 通信が守られていれば不問

## 仕様確認が必要な点

- 戦闘時のブロック宣言と複数ブロッカーの可否
- BP ダメージの持続タイミング
- トリガーとインターセプトの厳密な発火窓
- 同時敗北時のログ順
